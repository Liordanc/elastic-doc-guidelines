# Changelog Prompt (Specialized)

You are an expert technical writer for Elastic documentation.

Create changelog entries with the following requirements:

## Release Information
Version: [VERSION, e.g., "8.15.0"]
Release date: [DATE]
Product: [ELASTICSEARCH | KIBANA | LOGSTASH | BEATS | AGENT | OTHER]
Changes: [DESCRIBE CHANGES - can be multiple]

## Entry Format

Each changelog entry should:

1. **Start with a present-tense active verb**
   - Add
   - Fix
   - Improve
   - Update
   - Remove
   - Change
   - Support
   - Enable

2. **Describe WHAT changed**
   - Be specific
   - Name the feature or component
   - Example: "Add support for custom analyzers in text fields"
   - Example: "Fix memory leak in index rollover"

3. **Optionally explain WHY it matters**
   - If not obvious, add impact
   - Example: "...improving query performance by up to 30%"
   - Example: "...reducing memory usage during bulk indexing"

## Entry Examples

✓ "Add support for S3-compatible object storage in snapshot repositories"
✓ "Fix a bug that prevented aliases from updating during index rollover"
✓ "Improve query performance for large aggregations by 40%"
✓ "Update the default thread pool size for better multi-threaded performance"
✓ "Remove deprecated transport client code from the codebase"

✗ "The system now supports S3-compatible object storage"
✗ "Users can now use S3-compatible storage"
✗ "S3-compatible object storage is now supported"
✗ "We've made S3-compatible object storage available"

## Style Requirements

- **Tense**: Present tense, active voice
- **Focus**: "What" and "why", not "how"
- **Length**: One line per entry when possible
- **Tone**: Professional, direct, user-focused
- **Structure**: Consistent format for all entries

## Content Guidelines

- One change per entry
- Be concise but complete
- Focus on user impact
- Highlight improvements and new capabilities
- Include bug fixes, performance improvements, and feature updates
- Avoid generic phrases like "various improvements" or "internal updates"
- Include version/compatibility info if relevant
- Include migration notes if breaking changes

## Formatting Rules

- Use Markdown format
- Use version header: `# Version X.Y.Z` or `## Version X.Y.Z`
- Use bulleted list for entries
- Use code formatting for: commands, parameters, API names, settings
- Use bold for: UI element names, feature names (when needed)
- Use backticks for inline technical terms: `like_this`
- Keep lines scannable
- Order entries by importance or category

## Word Choice

✓ Use: add, fix, improve, update, support, enable, enhance, resolve
✗ Avoid: easy, new feature, now possible, the ability to, allows you to

## Organization (Optional)

You can group entries by category:
```
# Version X.Y.Z

## Features
- Add...
- Add...

## Bug fixes
- Fix...
- Fix...

## Performance
- Improve...

## Deprecations
- Deprecate...
```

## Output

Generate changelog entries in Markdown format.
- Use version header
- Use bulleted list format
- One action per entry
- Be concise and specific
- Include user impact when relevant
- Ready to publish
- No placeholder text

Now create the changelog entry/entries.
